No es el modelo. Es el método.

El LLM es la CPU. El contexto es la RAM. La spec es la fuente de verdad.

Tres piezas sostienen mi forma de trabajar: superpowers es el método, Sentinel es la puerta y Headroom es la factura. Cada cifra de esta página sale de un log, un audit real o una llamada a la tool MCP headroom_stats de esta misma máquina — no de un folleto.

01
Método

El operating loop

deep-change es el bucle operativo: compone las 14 skills de superpowers en cuatro fases —brainstorm → plan → execute → verify— y ajusta la ceremonia al riesgo: trivial = directo, sustancial = bucle completo.

1.1El bucle, fase a fase

  1. Brainstorm

    brainstorming

    gateno se escribe código antes de acordar el diseño.

  2. Plan

    writing-plans

    gateuna spec / plan de pasos verificables antes de tocar código.

  3. Execute

    subagent-driven-development test-driven-development

    gateel test antes que la implementación (TDD).

  4. Verify

    verification-before-completion requesting-code-review

    gateevidencia (comando + salida) antes de declarar «hecho».

1.2Las 14 skills de superpowers v6.3.0

Cuatro son leyes de hierro —invariantes que el bucle nunca salta—; las otras diez son herramientas que se invocan según la tarea lo pida.

  1. using-superpowersley de hierro · skills-first

    El bootstrap: invocar la skill relevante ANTES de cualquier respuesta o acción.

  2. brainstormingley de hierro · gate

    Explora intención, requisitos y diseño antes de cualquier trabajo creativo.

  3. writing-plans

    Convierte una spec en un plan de pasos verificables antes de tocar código.

  4. executing-plans

    Ejecuta un plan escrito en sesión aparte con checkpoints de revisión humana.

  5. subagent-driven-development

    Ejecuta el plan despachando un subagente fresco por tarea + revisión por tarea.

  6. test-driven-developmentley de hierro

    Escribe el test antes que la implementación, en cada feature o bugfix.

  7. systematic-debugging

    Ante cualquier bug o fallo, investiga la causa raíz antes de proponer el arreglo.

  8. verification-before-completionley de hierro

    Exige ejecutar comandos y confirmar la salida antes de declarar algo «hecho».

  9. requesting-code-review

    Pide revisión al completar features o antes de fusionar, para verificar el trabajo.

  10. receiving-code-review

    Recibe el feedback con rigor técnico y verificación, no con acuerdo performativo.

  11. finishing-a-development-branch

    Cierra el trabajo con opciones estructuradas: merge, PR o limpieza.

  12. using-git-worktrees

    Asegura un espacio de trabajo aislado antes de ejecutar un plan.

  13. dispatching-parallel-agents

    Lanza agentes en paralelo ante 2+ tareas independientes sin estado compartido.

  14. writing-skills

    Crea, edita y verifica skills antes de desplegarlas.

IntentGate

El arnés ANTES de ejecutar: intención real, alcance, criterios de éxito y supuestos.

Never-Stop

DENTRO de la ejecución: una vez aprobado el diseño, ejecutar hasta el final sin «¿sigo?».

Parallel-First

Topología: paralelo por defecto en workstreams independientes; secuencial solo si hay dependencia.

El gate + aprobación y el never-stop no se contradicen — uno es pre-ejecución, el otro intra-ejecución.

02
Spec-Driven Development

La spec es la fuente de verdad

El par spec → plan es la unidad de trabajo durable: sobrevive a la compactación del contexto. Cuando la ventana se llena y hay que descartar historial, la spec y el plan persisten en disco y reconstruyen el estado sin re-derivar lo ya acordado.

2.1El flujo

brainstorming → spec → writing-plans → plan → subagent-driven → ledger

Los nodos resaltados —spec, plan, ledger— son los artefactos durables que quedan en disco.

03
Las dos capas

Lo que me deja soltar el método

Dos capas de infraestructura son las que me dejan soltar el control y confiar en el bucle: Sentinel deja ejercer Never-Stop sin miedo —una puerta que bloquea lo catastrófico, así la ejecución autónoma no es temeraria—; Headroom deja sostener sesiones largas de spec → plan → execute comprimiendo el contexto para que la ventana no se llene a mitad de tarea.

3.1seguridadSentinel — la puerta

Un hook PreToolUse de coste cero que aplica a todas las tools (matcher: ""): se interpone entre cada acción y su ejecución.

acción → pipeline de hooks → DENY ASK WARN ALLOW

Fail-open por diseño: si el hook falla, deja pasar la acción — prioriza no romper el flujo sobre el bloqueo estricto.

El log tiene sesgo — y es honesto decirlo

El audit solo registra lo que se bloqueó, así que refleja mis propios hábitos, no una amenaza externa. El contador arranca el 3 de agosto de 2026, cuando monté esta máquina: no es un total de por vida. Y Sentinel es fail-open por diseño: si el hook falla, deja pasar. Es una red de seguridad calibrada para no estorbar, no un cortafuegos infalible.

Y son dos capas, no una. Los guards de bash (block-dangerous-commands.sh, destructive-guard.sh, secret-guard.sh) bloquean nada más instalar y no dependen de configuración. El preflight (sentinel_preflight.py) lee sus patrones de un iocs.json que el kit no distribuye —solo kit/sentinel/iocs.example.json como plantilla—: sin copiarlo, esa capa carga {} y deja pasar todo, y doctor.sh lo avisa con un WARN. Con el iocs.json puesto, ANTHROPIC_API_KEY sale como WARN, no DENY, y rm -rf / lo para el guard de bash, no el preflight.

Endurecido tras auditoría real con normalización de rutas (traversal ../) y split de comandos compuestos (a && b) para no dejar huecos.

04
Higiene de sesión

La rutina de una sesión fresca

El método rinde cuando la ventana está limpia. Tres hábitos de higiene mantienen el contexto = RAM disponible: anclar la ventana rodante al empezar el día, compactar a mano y no dejar que un contexto grande se convierta en la norma.

4.1El ping de las 6am

Mandar un ping a las 6:00 ancla la ventana rodante de 5 h justo al empezar la jornada, así el cupo se resetea con la ventana íntegra cuando de verdad vas a trabajar.

primer mensaje · 6:00 se resetea · 11:00
ventana rodante · 5 h
6:007:008:009:0010:0011:00
  • Es mecánica de suscripción, no de la API.
  • Los topes semanales van aparte de la ventana de 5 h.
  • Es un modelo mental de cómo se comporta, no un número garantizado por el proveedor.

4.2Tres disciplinas de sesión

  • /compact con instrucción plan A

    Compactar a mano, guiando qué conservar, es mejor que esperar al autocompact al 75 %: ese es el airbag, no el plan A.

  • opus[1m] solo si no cabe

    La ventana de 1 M se usa solo cuando el contexto no cabe, no para el trabajo rutinario.

  • Paralelizar independientes

    Solo workstreams independientes; los subagentes devuelven rutas y conclusiones, no vuelcan su contexto entero de vuelta.

05
Síntesis

Una sola filosofía

Las tres piezas no son tres herramientas sueltas: son una misma idea vista desde tres ángulos. El método dice qué hacer, Sentinel qué se permite y Headroom cuánto cuesta.

  • método · superpowers

    Qué hacer. El operating loop compone las skills en brainstorm → plan → execute → verify.

  • Sentinel

    Qué se permite. La puerta que bloquea lo catastrófico sin estorbar el flujo.

  • Headroom

    Cuánto cuesta. La factura en tokens y dólares, medida sin inflarla.

La idea que las une

Fail-open donde importa el flujo, medición honesta donde importa la confianza. Sentinel deja pasar si falla —para no romper el flujo—; Headroom mide su propio mérito sin inflarlo —para no romper la confianza—; y el método verifica con evidencia, no con afirmaciones.

5.1Mejoras honestas

Un backlog abierto, no una lista de fracasos: lo que aún no está y sé que debería estar.

  • Backup remoto de ~/.claude — es el único riesgo catastrófico: máquina de un solo disco; hoy no hay copia off-site.
  • Medir si Headroom rompe el prompt-caching — justificar el SPOF (un proxy en el camino) con números, o quitarlo.
  • Adelgazar CLAUDE.md — el fichero de instrucciones ha crecido; menos es más.
  • Cerrar los planes SDD abiertos — Task 3 (decisión de hooks) y el checkpoint R1 de Task 4 siguen pendientes.
  • Formalizar el uso de git worktrees para el aislamiento de ramas.
  • Higiene de la config de agentes — revisar el tiering de planner y el uso de subagent_type="Explore".
  • Rotar la key de Perplexity — pendiente.
