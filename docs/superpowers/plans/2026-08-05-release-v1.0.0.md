# Plan — cortar la release v1.0.0

## Contexto

El repo quedó funcionalmente listo para producción al mergear los PR #7, #8 y #9:
`main` con CI verde, 0 PRs abiertos, 16 suites de test en verde, y una
instalación limpia que da `10 PASS · 2 WARN · 0 FAIL` (los dos WARN son las
capas opt-in documentadas: IOCs de Sentinel y Capa 2 de secretos).

Lo que falta es la parte de *release*, y son dos cosas, ninguna funcional:

1. `CHANGELOG.md` tiene todo bajo `## [Unreleased]` y su cabecera dice
   literalmente *"Este proyecto aún no publica versiones etiquetadas; las
   entradas se agrupan bajo `[Unreleased]` hasta el primer tag."* Hay **0 tags**
   y **0 releases** en GitHub.
2. No existe proceso de release documentado. `CONTRIBUTING.md` documenta cómo
   correr los tests y cómo actualizar `gitleaks`, pero no cómo se corta una
   versión. Una release sin proceso escrito es una release irrepetible.

Ambas tareas son de documentación. **Ningún fichero de `kit/` cambia**, así que
el comportamiento instalado es idéntico antes y después.

## Global Constraints

- **Solo documentación.** No se toca nada bajo `kit/`, ni `.github/workflows/`,
  ni `Makefile`. Si una tarea parece necesitarlo, es que la tarea está mal:
  paren y repórtenlo.
- **Español**, tuteo, y el tono del repo: afirmaciones verificables, sin
  superlativos. Lo que no se pueda verificar, no se escribe.
- **`bash kit/scan-secrets.sh .` tiene que seguir dando `PASS`.** Rechaza emails
  que no sean `@example.com`, `@example.org` o `noreply@`, y las rutas absolutas
  del home de la cuenta root. Su regex de emails marca además los destinos SSH
  con forma usuario-arroba-host, que no son emails.
  **Y este documento está sujeto a esa regla como cualquier otro fichero del
  repo**: si necesitas nombrar uno de esos patrones, descríbelo con palabras en
  vez de escribirlo literal, o el propio escáner marcará el plan.
- La versión es exactamente **`1.0.0`** y el tag **`v1.0.0`** (con `v`). La
  fecha de release es **2026-08-05**.
- El formato del CHANGELOG es [Keep a Changelog](https://keepachangelog.com/es-ES/1.1.0/)
  y se mantiene: no se renombran las secciones existentes (`Fixed`, `Added`,
  `Changed`, `Documentation`) ni se reordena su contenido.
- No se crea el tag ni la release de GitHub en estas tareas: eso lo hace quien
  controla el plan, después de que el review final esté limpio. Ver
  "Pasos posteriores al merge".

## Task 1 — `CHANGELOG.md`: cortar la versión 1.0.0

Tres cambios en `CHANGELOG.md`, y nada más.

**1.1 — La nota de cabecera.** Sustituir estas tres líneas:

```
Este proyecto aún no publica versiones etiquetadas; las entradas se agrupan
bajo `[Unreleased]` hasta el primer tag.
```

por:

```
Este proyecto sigue [Versionado Semántico](https://semver.org/lang/es/).
`[Unreleased]` recoge lo que ya está en `main` y aún no se ha etiquetado.
```

**1.2 — Partir la sección.** Donde ahora hay una única línea `## [Unreleased]`,
dejar exactamente esto, conservando **todo** el contenido actual bajo la nueva
cabecera de versión y sin tocar una palabra de ese contenido:

```
## [Unreleased]

## [1.0.0] - 2026-08-05

Primera versión etiquetada. Recoge el kit completo: guards deterministas con
suite de test falsable, 8 agentes con tiering, dos capas de secretos, eval set
opt-in, y `install.sh`/`doctor.sh` como bucle de instalación y diagnóstico.
```

Es decir: `## [Unreleased]` queda **vacío** (sin subsecciones), y el contenido
que había pasa entero a `## [1.0.0] - 2026-08-05`, precedido por ese párrafo de
resumen.

**1.3 — Enlaces de comparación al final del fichero.** Añadir al final, tras una
línea en blanco:

```
[Unreleased]: https://github.com/manuelcozar55/setup-claude-code/compare/v1.0.0...HEAD
[1.0.0]: https://github.com/manuelcozar55/setup-claude-code/releases/tag/v1.0.0
```

**Verificación de la tarea** (ejecutar y pegar la salida en el informe):

```bash
# 1. las dos secciones existen, y en este orden
grep -n '^## \[' CHANGELOG.md
# 2. [Unreleased] esta vacio: no debe haber ninguna linea '### ' entre las dos
awk '/^## \[Unreleased\]/{f=1;next} /^## \[1\.0\.0\]/{f=0} f && /^### /{print "CONTENIDO INESPERADO: "$0}' CHANGELOG.md
# 3. no se ha perdido contenido: el recuento de vinetas de primer nivel
grep -c '^- ' CHANGELOG.md
# 4. el scanner sigue contento
bash kit/scan-secrets.sh .
```

El punto 3 debe dar **el mismo número antes y después** del cambio: mide `git
stash`/`git stash pop` si hace falta, o compara con
`git show HEAD:CHANGELOG.md | grep -c '^- '`. Si baja, se ha perdido contenido y
la tarea no está hecha.

## Task 2 — `CONTRIBUTING.md`: documentar cómo se corta una release

Añadir al final de `CONTRIBUTING.md` una sección nueva, `## Cortar una release`,
con este contenido exacto:

```markdown
## Cortar una release

El versionado es [SemVer](https://semver.org/lang/es/). Como este repo es un kit
de configuración y no una librería, la regla práctica es:

- **MAJOR** — un cambio que rompe una instalación existente: `install.sh` deja de
  ser idempotente sobre la versión anterior, un guard cambia de contrato, o
  `settings.json` deja de ser compatible.
- **MINOR** — piezas nuevas que no rompen nada: un guard más, una suite de test,
  un documento, un flag de `install.sh`.
- **PATCH** — arreglos y documentación.

El orden importa: **verificar primero, etiquetar después.** Un tag es inmutable
en la práctica (alguien puede haberlo clonado), así que no se corta una versión
sobre algo sin comprobar.

```bash
# 1. main al dia y limpio
git checkout main && git pull --ff-only && git status --porcelain   # sin salida

# 2. las 16 suites y el escaner de secretos
make test                    # exit 0
bash kit/scan-secrets.sh .   # PASS

# 3. la prueba que de verdad importa: instalacion limpia en un CLAUDE_HOME virgen
T=$(mktemp -d)
CLAUDE_HOME="$T/h" bash kit/install.sh
CLAUDE_HOME="$T/h" bash kit/doctor.sh   # exit 0, 0 FAIL
rm -r "$T"

# 4. mover el CHANGELOG: [Unreleased] -> [X.Y.Z] - AAAA-MM-DD, dejar
#    [Unreleased] vacio, y añadir los dos enlaces de comparacion del final

# 5. etiquetar y publicar
git tag -a vX.Y.Z -m "vX.Y.Z"
git push origin vX.Y.Z
gh release create vX.Y.Z --title "vX.Y.Z" --notes-file <(sed -n '/^## \[X.Y.Z\]/,/^## \[/p' CHANGELOG.md)
```

Nota sobre el paso 3: los dos `WARN` de `doctor.sh` en una instalación limpia
(IOCs de Sentinel y Capa 2 de secretos) son correctos — son capas opt-in, y
`doctor.sh` sale con 0 igualmente. Lo que bloquea una release es un `FAIL`.
```

**Verificación de la tarea:**

```bash
# la seccion existe y los bloques de codigo estan balanceados
grep -n '^## Cortar una release' CONTRIBUTING.md
python3 -c "import pathlib; t=pathlib.Path('CONTRIBUTING.md').read_text(); n=t.count('\`\`\`'); print('fences:', n, 'par' if n%2==0 else 'IMPAR-ROTO')"
bash kit/scan-secrets.sh .
```

Ojo con el markdown: la sección contiene un bloque ` ```bash ` **dentro** de un
bloque ` ```markdown `. Si al pegarlo se rompe el anidamiento, el fichero queda
con fences impares y la verificación lo detecta. Si no logras anidarlos, escribe
la sección sin el envoltorio ` ```markdown ` — el contenido es lo que importa,
no el envoltorio.

5. Comprobar que la release aparece y que el enlace de comparación del CHANGELOG
